# Release Process

This project uses GitHub Releases as the changelog surface and PyPI publishing
trigger. Releases must be tag-first so `release-notes-scribe` can draft the
GitHub Release notes before the release is published.

## Required Local Checks

Run the standard validation loop before tagging:

```bash
pdm run check
```

`pdm run check` runs:

```bash
pdm run contracts:check
pdm run pytest
pdm run ruff check src tests
pdm build
```

## Process

1. Choose the next semantic version tag, for example `v0.3.2`.
2. Create and push the tag:

```bash
git tag v0.3.2
git push origin v0.3.2
```

3. Wait for the `Create Draft Release` GitHub Actions workflow to complete.
   It calls the ordinary `Python package` CI workflow against the tagged commit.
   Every supported Python version (3.12, 3.13, and 3.14) must pass lockfile,
   contract, generated-binding, test, lint, build, and strict Twine archive
   checks before Release Notes Scribe creates the actual GitHub draft release.
4. Review the drafted GitHub Release generated by
   `btfranklin/release-notes-scribe`.
5. Publish the GitHub Release.
6. Confirm the `Upload Python Package` workflow completes.

## Ordering Constraint

Do not publish the GitHub Release before pushing the tag and letting the
`Create Draft Release` workflow run. Release notes are generated by the
tag-triggered workflow in `.github/workflows/create-draft-release.yml`.

Creating a draft manually in GitHub does not trigger the tag workflow and does
not establish that validation passed. The supported validated-draft path is to
push the tag, wait for all checks and the generated draft, review, then Publish.
Keep the validated tag unchanged through publication.

Publishing the GitHub Release triggers `.github/workflows/python-publish.yml`.
It trusts the completed draft preparation, checks out the release's tag with
full history for SCM versioning, rebuilds the wheel and source archive, and
uploads them to PyPI through Trusted Publishing in the existing `release`
environment. It does not rerun validation or install development dependencies.
No draft archives or prior workflow runs need to be recovered. Publishing a
manually created release bypasses draft validation; follow the tag-first path.
